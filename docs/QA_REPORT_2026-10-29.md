# PerfectKaraokeEternal — software QA review

**Date:** 2026-10-29  
**Branch:** `develop`, baseline commit `6524803c` (tree clean)  
**Environment:** Windows, Node v24.15.0, npm 11.12.1, Chromium preview via the app's static server  
**Scope:** lyrics (`.lrc`/`.elrc`), playback, queue, CD+G rendering, MP4 audio tracks, file access, static server, and the reliability plan in [UPSTREAM_ISSUE_ROADMAP.md](UPSTREAM_ISSUE_ROADMAP.md).

## 1. Verdict

**Conditional pass for local, single-user desktop use on Chromium/Edge.** No known P1 or P2 defects remain in the tested paths, the automated suite is green, and the three verified regressions found during this review are fixed.

**Not ready for LAN or hosted use.** The app has no authentication by design; the server now defaults to loopback and must be opted into LAN exposure explicitly.

Residual risk is concentrated in what this environment cannot exercise: Safari's native audio-track API, the Windows File System Access folder picker/permissions, fullscreen in a normal desktop browser, and long real-world library/track soak tests.

## 3. Findings, by severity

### F1 — High: static server exposed the whole repository and listened on all interfaces (FIXED)

- **Verified before the fix:** `netstat` showed `0.0.0.0:4317` (and `[::]:4317`) listening. `curl` returned `200` for `/.git/config`, `/package.json`, `/package-lock.json`, `/serve.js`, `/test/lrc.test.js`, `/docs/UPSTREAM_ISSUE_ROADMAP.md` and `/node_modules/eslint/package.json`.
- **Impact:** anyone on the same network could read repository internals, including `.git/config` (which can contain remote credentials) and any loose files in the checkout. This contradicted the required local-only default.
- **Fix:** [serve.js](../serve.js) now resolves the request first, rejects anything outside the root with 403, and serves only `index.html`, `css/`, `js/` and `assets/`; everything else inside the repository returns 404. Raw and percent-encoded backslashes are normalized before resolution. The listener defaults to `127.0.0.1`; `--host`/`HOST` is an explicit opt-in with a console warning.
- **Tests:** `test/serve.test.js` covers the allowlist, internal-path 404s, asset MIME type, traversal (raw/encoded), malformed URLs, host parsing and LAN opt-in. Live checks after the fix: loopback-only listener; internals 404; `--host 0.0.0.0` prints the network warning and still serves only app files.
- **Status: PASS.**

### F2 — Medium: macOS AppleDouble files in ZIPs became phantom songs (FIXED)

- **Reproduction:** a ZIP containing the real `Song.mp3`/`Song.cdg` plus `._Song.mp3`/`._Song.cdg` produced **two** tracks, because the resource forks share the audio extension and pair with each other. Playback of the phantom entry fails, and the scan result misleads the user.
- **Fix:** [js/library.js](../js/library.js) ignores entries whose basename starts with `._` (in addition to `__MACOSX/` and `.DS_Store`).
- **Test:** `buildLibrary ignores AppleDouble entries in zips` expects one track and no warnings; it failed before the fix and passes now.
- **Browser check:** a generated multi-song ZIP with `__MACOSX/` and `._…` entries loaded exactly two playable tracks and no warnings.
- **Status: PASS.**

### F3 — Medium: pressing Next after a song ended duplicated it in “Played” (FIXED)

- **Reproduction:** with the queue empty and a track already ended (`finished = true`), each Next click appended the same track to the history. Browser evidence before the fix: one Next grew `[First, First, Second]` to `[First, First, First, Second]`, and a second Next added it again.
- **Root cause:** `playNext()` pushed `state.currentId` unconditionally, while `handleEnded()` had already recorded that play.
- **Fix:** [js/app.js](../js/app.js) only records the current track when it has not already finished, matching the existing guard in `playNow()`.
- **Evidence after the fix:** natural end pushed history 4 → 5; Next left it at **5**; replay/Play restarted at 0.61 s with history unchanged.
- **Automated coverage:** none yet — queue state lives in the DOM module. Browser-verified; adding a pure queue-state test is in the roadmap.
- **Status: PASS (browser-verified).**

### F4 — Low: filenames that reduce to an empty artist or title produced blank rows (FIXED)

- **Reproduction:** `The Beatles - [Karaoke]` loses its entire title when the karaoke suffix is stripped, leaving `The Beatles - `. The parser returned `artist: 'The Beatles', title: ''`, so the library showed a blank song row. ` - Title` produced a blank artist.
- **Fix:** `parseTrackName()` rejects either empty side; the scanner reports the file as skipped instead of adding a broken row.
- **Test:** `parseTrackName rejects names that leave an empty artist or title` plus the full legacy parser table; all pass. A browser scan of a valid pair still behaves normally.
- **Status: PASS.**

### F5 — Low, open: malformed `.lrc` is accepted at scan and only fails at play (DEFERRED)

- A `.lrc` with no timestamped lines still pairs with audio and appears in the library. Choosing it shows a clear, non-fatal error: “no usable lyric lines in the .lrc or .elrc file”. This differs from ELRC-only lyrics, which are content-checked during the scan.
- **Why deferred:** validating every LRC adds a second read of each lyric file and changes scan cost; the current failure is contained and explains itself. A future change could validate at scan or badge unplayable lyric tracks. No data loss or crash.
- **Status: DEFERRED (not a release blocker).**

### F6 — Low, open: LRC `[offset:±ms]` is ignored (DEFERRED)

- The parser treats `[offset:…]` as metadata and does not shift timings. Files that use the tag will be out of sync by the stated offset. The reference implementation in `chord-vault/src/karaoke-player` also ignores it, and no real offset-bearing sample was available. The sign convention should be confirmed against a real file before implementing.
- **Status: DEFERRED (documented limitation).**

### F7 — Low: documentation drift on test counts (ADDRESSED)

- The roadmap's historical verification section says 44 tests; the suite is now 72. A dated note was added to [UPSTREAM_ISSUE_ROADMAP.md](UPSTREAM_ISSUE_ROADMAP.md) rather than rewriting the historical audit. The server-hardening item in that plan is marked done.

### Not defects / verified plans

- **#55 (text background does not match text): PASS for this implementation.** The upstream screenshot shows a stale, too-small backdrop while more lyric lines appear; the reporter noted a repaint fixed it. Here the backdrop is positioned from `contentBounds` after every changed CD+G frame and on every seek/resize. With a purpose-built CD+G whose lyric area grows:
  - t=1 s: bounds `[60,96,90,108]`, backdrop `[50,86,100,118]`;
  - t=3 s: bounds `[30,96,150,180]`, backdrop `[20,86,160,190]`;
  - t=5 s: bounds `[12,48,186,180]`, backdrop `[2,38,196,190]`;
  - seeking back to 1 s restored the small bounds and backdrop exactly.
  The real MP3+G fixture behaved the same way (backdrop exactly content bounds plus the 10 px pad). A decoder regression test now locks in growth and reset.
- **#79 (audio-track switching): PARTIAL, implementation verified; native Safari BLOCKED.** Chromium reports `'audioTracks' in HTMLMediaElement === false`, so the selector is correctly hidden and the default track plays. With a simulated two-track API on the video element, the selector showed “Vocal”/“Instrumental”, switching enabled exactly one track, playback position did not move (delta 0), the choice was saved per file (`pke.prefs.v1`), and it was restored after reload. Real multi-audio-track MP4 playback still needs Safari.
- **#91 (scan resilience): PASS.** Corrupt ZIP + valid pair in the browser produced “1 song loaded · 1 skipped” with the archive path and “Not a ZIP file (end record not found)”; the scan continued. Unit tests cover unreadable files/folders.
- **Fullscreen: BLOCKED in this environment.** `document.fullscreenEnabled` is true and the button receives focus, but the embedded preview never changes `document.fullscreenElement`; the earlier audit saw the same. The standard `requestFullscreen`/`exitFullscreen` path and error toast are in place; verify in a normal desktop browser.
- **Native folder picker / Windows drive selection / permissions: BLOCKED.** Headless automation cannot drive `showDirectoryPicker` or the Windows permission prompt. Drag-and-drop scanning and the File System Access code path were reviewed; the picker/permission flow remains a manual check.
- **Missing files after a scan: NOT RUN.** The player converts a failed media read into a visible playback error; a real deleted-file test requires a live folder handle.

## 7. Remaining roadmap (justified work only)

**P1 — none.**

**P2 — manual verification before calling the release broadly ready**
1. **Safari with a real multi-audio-track MP4.** Confirm two labelled tracks, switching during playback, unchanged position, per-file memory and cleanup on track change. Chromium's simulated path already passes; the native API is unverified.
2. **Windows File System Access matrix.** Open a folder through the picker, deny/allow permission, reopen the remembered folder, rescan after adding/removing files, play a file deleted after scanning, and try an unreadable folder. These were BLOCKED in automation.
3. **Desktop browser matrix and soak.** Fullscreen, Firefox playback, a large real library and a long track. The current evidence is Chromium only and the preview cannot enter fullscreen.

**P3 — small correctness/quality follow-ups**
4. **Automated queue-state tests.** The history/queue bug was only browser-verified because the state lives in the DOM module. Extracting the transition logic into a pure module would make duplicate/next/replay/clear regressions cheap to test.
5. **Decide LRC `[offset]` support** using a real file, and validate LRC content at scan (or badge it) so the library's “unusable files are reported” promise matches playback behavior.
6. **Optional server hardening:** reject symlinks that resolve outside the public directories. No symlinks exist today and the allowlist already blocks repository internals, so this is defense in depth, not a known defect.

**Deliberately not done:** custom backgrounds, pitch shifting, scoring, YouTube download, React, databases, accounts, rooms, and new runtime dependencies. None is justified by a demonstrated defect, and each conflicts with the standalone local-player scope.

## 8. Against the reliability plan

- **Phase 0 — complete.** CD+G keying, resilient scanning (#91), multi-song/deflated ZIPs, Play Now queue consumption, duplicate queue entries, audio-track ids and the test/lint baseline were re-verified. The only new Phase 0-class defect was the queue history duplication (F3), now fixed.
- **Phase 1 — partially complete.** #55 was investigated with a reproduction of its failure mode and now has automated bounds coverage. The Chromium browser matrix was executed; Firefox and Safari remain manual. #79 is implemented and passes under a simulated API, but native Safari is BLOCKED. Static-server hardening was originally a P3 “consider” item; it was brought forward because the verified exposure (F1) contradicted the required local-only default and allowed unauthenticated LAN access to repository internals.
- **Phase 2/3 — untouched.** Custom backgrounds, pitch shifting, multi-folder libraries, scoring, push, proxy auth and YouTube download remain deferred or out of scope, as the plan recommends. No speculative feature was added.
- **Deviation from the plan:** server hardening was treated as required rather than optional. Everything else followed the plan's smallest-change sequencing.

## 9. Release readiness and next actions

- **Local single-user release on Chromium/Edge:** **conditional GO.** The default server is local-only, the core media paths work with real fixtures, and the queue/lyrics/CD+G regressions are fixed and covered.
- **LAN, shared or hosted use:** **NO-GO.** There is no authentication by design; LAN exposure is now an explicit opt-in and should be documented as trusted-network-only.
- **#79:** **PARTIAL.** The UI, labels, single-track selection and per-file memory are implemented and verified under a simulated API; native Safari validation remains.

**Next three actions**
1. Run the Safari multi-track and Windows folder-picker/permission manual matrix.
2. Add pure queue-state tests (history, next, replay, clear) and keep the current browser scenarios as a smoke checklist.
3. Decide the LRC `[offset]` behavior and whether malformed LRC should be rejected at scan; update the README with the chosen behavior.
